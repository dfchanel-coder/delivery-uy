# ADR-009 - Identifiers, Timestamps, Soft Delete and Tenancy

Status: ACCEPTED

## Context

Public identifiers appear in APIs, support conversations and (potentially) printed
documents. AGENTS.md section 27 requires collision-resistant, non-predictable
public identifiers. Auditability requires timestamps that survive time-zone and
schema changes. Financial and audit records must be immutable and preserved
(AGENTS.md sections 28, 92).

## Decision

### Identifiers

- Primary keys: `uuid` generated by the database
  (`uuidv4()` default via Prisma `@default(uuid())`).
- Public-facing references use **separate, human-quotable codes** (for example
  `Order.code`, `Ticket.reference`) generated from a time-ordered random
  alphabet (base32 Crockford, at least 10 characters, collision-checked).
- Sequence-like values that must be monotonic (for example audit ordering or
  settlement numbers) use database sequences, never client-generated values.
- Foreign keys are internal UUIDs; they are never used as authorization proof
  (AGENTS.md section 32).

### Timestamps

- All timestamps are `timestamptz` stored in UTC (AGENTS.md section 73).
- Prisma fields are named `...At` (`createdAt`, `updatedAt`, `deletedAt`).
- Business wall-clock concepts (`City.timezone`, `MerchantSchedule.openTime`)
  store a time-of-day without date plus an IANA timezone reference. Never store
  "local datetime without zone".
- APIs serialize to ISO 8601 with `Z` suffix.

### Soft delete

- Soft delete (`deletedAt`) applies to: `User`, `Address`, `Merchant`,
  `Product`, `ProductImage`, `Favorite`, `Category`, `DriverDocument`.
- Hard delete is used only for transient operational data: sessions, expired
  tokens, idempotency keys, rate-limit counters, `DriverLocation` beyond
  retention.
- Immutable / append-only tables (no `deletedAt`, no `updatedAt` in the
  business sense): `AuditLog`, `OrderTimeline`, `LedgerEntry`,
  `JournalEntry`, `PaymentWebhookEvent`, `DeliveryCodeAttempt`, `RiskEvent`.
- Deleting a user never deletes orders, payments, ledger entries or audit logs
  (AGENTS.md section 92). Personal data in orders is retained as legally
  required and minimized otherwise.

### Transactions

- Multi-table writes that must succeed or fail together use a single explicit
  transaction (`prisma.$transaction`). Order creation, payment approval,
  delivery completion and settlement posting are examples
  (AGENTS.md sections 83, 84).
- Domain events emitted in the same transaction are written to `OutboxEvent`
  so notification/analytics listeners never depend on in-process delivery.

## Consequences

- Every list query that reads soft-deleted entities must filter
  `deletedAt: null` explicitly; this is enforced by central query helpers in
  `packages/database`, not left to individual services.
- UUID primary keys are larger than integers; acceptable given security
  requirements.
- Audit-oriented append-only tables grow monotonically and require retention
  and archival policies (see `DATABASE.md`).
